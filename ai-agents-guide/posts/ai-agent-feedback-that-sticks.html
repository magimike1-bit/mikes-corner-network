How to give an AI agent feedback it will actually use

Working With Agents · 9 min read

Why does an agent accept a correction, fix the output in front of you — and then make the identical mistake next week?

Because the correction probably never reached the place the agent reads. A scheduled agent starts each run fresh, with no memory of the last three times it was told otherwise; a correction that is never written down anywhere durable is a conversation that evaporates the moment the run ends. The repeat mistake looks like a competence problem. It is a storage problem. Fixing it takes two skills: writing a correction the agent can act on, and putting that correction where it will be re-read.

First, the correction itself: what, why, and how

For the answer in front of you, a three-part formula does the work: what is wrong, why it is wrong, and how it should change. "Too technical — this is for people new to the topic — rewrite it in simple words, short sentences, with one everyday example" gives the agent a defect, a reason, and a direction. "Make it better" gives it none of the three, and vague feedback reliably produces vague improvements.

Three habits sharpen the formula further. Be specific: name the length, tone, audience, or format instead of the feeling. Show an example of the target where you can — and an example of what to avoid, since a negative example fences off the failure you keep seeing. And correct one thing at a time: a stack of simultaneous instructions gets partially followed, and you cannot tell which part failed.

That handles today's output. It does nothing for next week's run, because all of it happened inside a chat.

Where the correction lives decides whether it sticks

Corrections land in one of three places, and none of them is memory. The chat thread or run log: you typed the fix, the agent acknowledged it, the thread scrolled on — and a fresh run opens a new context and never re-reads it. The prompt or instruction text: patches accumulate there until they are buried, ignored, or deleted by someone who did not understand a line. Or nowhere: the output got fixed by hand, the corrected version went out, and from the agent's point of view the run succeeded.

The middle rows hide a distinction worth keeping. A rule and a lesson are different objects. A rule states a condition: "classify by what the purchase is for, not by words in the vendor name" transfers to new cases; "put Vendor X under software" does not. A lesson keeps the why — the vendor name misled the classifier — which is what lets the agent handle the next misleading name instead of only the recorded one. Store the rule in the instructions; store the lesson, with its why, where the agent can pull it up for similar work.

The second-time rule: a procedure for repeat mistakes

The trigger is a count, so keep a log — one line per correction, dated. Without a log, nobody can say how many times a correction has been given, and the count is the whole mechanism:

  1. First time: fix the output, and log the correction. Use the what/why/how formula, get today's work right, and write the one-line log entry while the details are fresh. A correction captured a week later is a correction half-remembered.
  2. Second time: fix the instructions, not the output. The same correction twice means the problem is a missing rule, not a bad answer. Restate the correction as a general rule — condition, not example — and add it to the instructions, brief, or runbook the agent reads at the start of every run, in the same pass as the fix.
  3. Before the next run, confirm the instructions are actually loaded. A rule in a file the setup never reads is the chat thread with extra steps.
  4. Third time, or any error too costly to repeat once: stop relying on memory at all. Move the catch into a mechanism — a pre-send checklist the agent must complete, a validator, an approval step, or an automatic block where the tool supports one. Mechanical checks do not get tired and do not forget.
  5. Retire stale lessons. Vendors rename things, policies change, corrections get superseded. Stored feedback needs an owner and an occasional review, or yesterday's lesson becomes tomorrow's repeat mistake.

What success looks like: the log shows the same correction stopping at one or two entries, new mistakes replacing repeats, and any third occurrence caught by a check rather than by you.

When the loop is the problem, not the feedback

Inside a single stuck session, more feedback can make things worse. A retry does not start clean: its context already contains the failed attempt, the frustrated correction, and the agent's explanation of what it thought it fixed — so attempts compound the noise instead of converging. Two rules follow. Never send "try again" or "still broken" twice in a row; a repeated low-information prompt changes nothing except the agent's confidence. And before another attempt, return the work to the last known-good state — the last version you recognised as right — instead of stacking a new attempt on top of a broken one. Then give the corrected instruction once, against the clean state.

Prove it stuck: the fresh-session test

Do not grade a correction by the agent's acknowledgement. Grade it by behaviour, in conditions that cannot cheat:

  1. Open a new session or wait for the next scheduled run. The test only means something if the agent cannot lean on the chat where the correction happened.
  2. Give a probe task that would trigger the old mistake — a new case of the same type, not the original example. Passing the original example proves memorisation of one case; passing a fresh case proves the rule transferred.
  3. Check the output against the rule, not against your mood. A short pre-return checklist helps here too: does the output meet every stated requirement, does it avoid the previously identified mistakes, is anything required missing?
  4. Record the result in the log. Probe passed: the correction is in force. Probe failed: that is occurrence number two (or three) — escalate it one row down the table instead of re-sending the same chat message.

None of this asks for a smarter model. It asks for corrections written as rules with reasons, stored where the agent reads, counted so repeats trigger escalation, and tested cold. Agents repeat the mistakes whose corrections evaporated. Write the correction down in the right place, and the mistakes it makes next week are at least new ones.
