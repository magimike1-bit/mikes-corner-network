AI Agent Permissions: Give an Agent the Least Access That Does the Job

When an AI agent goes wrong, the post-mortem almost never reads 'the prompt was not polite enough'. It reads: the agent could delete, send, pay, or publish — and did. Permissions are the control that decides how much damage a mistake, or a manipulation, can do. Here is how to set them like an adult.

Published 2026-10-19 · Last updated 2026-10-19

The blast radius is set by permissions, not by the prompt

Every AI agent is, from a security point of view, a new kind of insider: it holds credentials, touches real systems, and acts faster than any human can watch. It also takes instructions from an unusually dangerous place — its inputs. Documents, emails, web pages, and files an agent reads can contain text crafted to redirect it, which means “the agent was told to behave” is not a control at all. The control that survives a manipulated or simply mistaken agent is the one enforced outside the model: the permission set that decides what the agent can do, whatever it currently wants to do.

That is why experienced practitioners repeat one sentence until it bores them: the blast radius of an agent is set by its permissions, not by its prompt. A read-only research agent that gets manipulated can produce a bad report. A write-everywhere agent with the same manipulation can produce a bad week. Least privilege — the minimum access a specific task requires, enforced per agent — is how you choose which of those outcomes is even possible.

The starter permission table

Match access to the task, not to your optimism
Agent taskGrantRefuse by default
Research, summarise, monitor, auditRead-only access to the specific sourcesAny write, send, or delete capability
Draft emails, posts, documentsWrite to a drafts location onlySending or publishing — a human sends
Update records, tickets, spreadsheetsWrite to those records, in that toolDeleting records, changing ownership, billing changes
Customer-facing answersRead approved knowledge; draft repliesRefunds, discounts, order changes, promises
Anything financial, destructive, or publicPrepare the action for approvalExecuting it without a human confirming the actual action

Two habits make the table real rather than decorative. One identity per agent: each agent gets its own account, keys, or scoped token — never a shared login, and never your personal admin credentials. Separate keys per agent or per job mean a problem agent can be cut off in one move, and your logs can answer the question every incident asks first: which agent did this? Credentials stay out of the model's sight: keys live in the platform's secret storage or your password manager, are attached by the system at run time, and never appear in prompts, documents the agent reads, or logs it can browse. A secret an agent can read is a secret it can repeat.

Time is a permission too

Standing access — credentials that work forever, waiting — is where quiet risk accumulates. Prefer the opposite wherever the platform allows it: short-lived or task-scoped access that expires, separate credentials for reading versus modifying, test or staging access before production access, and different credentials for each so a mix-up is visible rather than silent. Then add the calendar habit that keeps it all honest: a short monthly review where you list every agent, the access it holds, and the last time that access was actually used. Access an agent has not needed in a month is access it should lose until it needs it again. Permission creep is not a scandal; it is the default outcome of never looking.

The human gate: a short list, kept sacred

  1. Deleting anything — files, records, accounts, environments. Deletion is irreversible in a way a mistaken edit is not.
  2. Sending anything outward — emails, messages, posts, or submissions in your name or your business's name.
  3. Spending anything — purchases, refunds, payments, plan changes, or commitments that create them.
  4. Changing access itself — creating accounts, granting permissions, changing security or network settings.

For everything on that list, the agent prepares and a person confirms the concrete action — not a summary of it, the action itself — before it executes. Everything off the list can run at the speed agents are good at. That split is the whole philosophy in one line: autonomy is something an agent earns task by task, inside boundaries a person set while calm — not a default you discover during an incident.

What success looks like: you can produce, in two minutes, a list of your agents, the exact access each holds, and the last time each permission was used — and every irreversible action in the past month shows a human confirmation next to it.

Questions people ask about agent permissions

Isn't this overkill for a personal agent? Scale the ceremony, not the principle. A personal agent might need three lines in a notebook instead of a policy document — but read-only by default, its own login, and a human tap on sends and spends are as cheap at home as they are wise at work.

The tool only offers one all-access key. Now what? Then the tool is the boundary: give the agent a limited account or workspace inside it (a folder, a project, a draft space) and keep the all-access key out of the agent entirely. If neither is possible, that tool gets a drafting agent, not an acting one.

What should I log? Enough to reconstruct an incident: which agent, what it did, when, on what, and who approved it if approval was required. Logs you never test are decoration — glance at them monthly, in the same review where you prune permissions.

Your first permission audit, in twenty minutes

If your agents are already running with access granted in the enthusiasm of setup day, this audit is the way back. List every agent you have, including the ones you have half-forgotten — especially those. For each, write down three things: what it can read, what it can change or send, and which credentials it holds. Compare that list against the starter table in this article and mark every place the agent holds more than its task needs. Downgrade in the order of danger: remove send and delete rights first, then production access, then anything the agent has not touched in a month.

Where a platform makes downgrading awkward, use the practical fallbacks the security literature offers: a separate limited account, a drafts-only workspace, a scoped key for the specific job, or simply moving the agent to prepare-only mode for the risky step while a person executes it. Then schedule the monthly ten-minute version of the same review, because permissions drift back — every “just this once” grant is permanent until somebody looks. The audit's real product is not the tightened list, satisfying as that is. It is the sentence you will be able to say after any future incident, truthfully and immediately: here is exactly what that agent could reach, and here is the record of what it did. In a world of agents that act while you sleep, that sentence is worth more than any single tool you can buy.
