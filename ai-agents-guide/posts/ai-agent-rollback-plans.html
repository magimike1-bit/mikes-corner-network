AI agent rollback plans: undoing a bad run safely

Safety · 8 min read

Can one button undo a bad agent run?

No. Parts of a run can be restored, parts can only be corrected, and a few parts cannot be taken back at all. A rollback plan that pretends otherwise fails at the worst moment — during the incident, when someone reaches for an undo that covers an action it never covered. The workable plan names three layers in advance, and says plainly which actions sit in each one.

Three layers: what each one can and cannot reverse

LayerWhat it reversesWhat it does not reverse
Version or checkpoint restoreFiles, configuration and the agent's own setup, returned to a previous versionData changes made by the run, and anything that left the system
Compensating actionsData and task changes, by carrying out a planned opposite actionThe original event itself — a correction follows it, the record keeps both
Correction onlyNothing is reversed; the error is acknowledged and fixed forwardA sent email, a captured payment, a delivered webhook, an irreversible third-party call

The first layer has a second catch. A checkpoint restore is not the same as a production rollback: a published app restored to a checkpoint still has to be republished before users see the restored version. Treating “restored” as “live” leaves the bad version in front of users while the operator believes the incident is over.

The second layer is the one most plans miss. Version rollback does not undo data changes. Data changes need their own opposite action, designed while the forward action is designed — not invented under pressure.

The one-page abort plan, written before the incident

Keep the plan to one page, stored where the person on duty can reach it without logging into the system that just failed. A complete plan covers five things: detection, shutdown, manual fallback, reversal of completed actions, and incident documentation.

Detection names the signal that a run has gone wrong — wrong recipient, wrong record count, actions arriving faster than expected — and who can declare the abort. Shutdown is the fastest way to pause the agent, tested in the drill below. Manual fallback states how the underlying work continues by hand while the agent is stopped, even if the answer is “it waits.” Reversal points to the compensating-action list in the next section. Documentation is one short record: what ran, what was reversed, what was corrected, and what remains open.

Then apply the decision rule that gives the page its teeth. Any action with no undo is a decision: add an approval step before that action, or accept the risk knowingly and write that acceptance on the page. An unlisted irreversible action is not a risk that was accepted. It is a gap that was missed.

Compensating actions: the undo built in advance

For every action the agent can take, write the forward action and its compensation as a pair:

Forward actionCompensating action
Create a task or recordDelete or cancel that task or record
Update a fieldRestore the previous value — which means the previous value is saved before the update
Send an external emailSend a correction — the original email is not recalled, it is followed by a fix
Capture a payment or call a third-party serviceNo compensation exists; route the action through the approval rule above

One related safeguard belongs in the same list. Retried actions must not run twice. Idempotency — the property that repeating a request does not repeat its effect — is enforced by the tool runtime, not by the model. In plain terms: do not rely on the agent remembering that it already sent, created or charged something. The system underneath it has to carry that protection, and the abort plan should name where it lives.

Stop the run: the rollback procedure

  1. Revoke or pause the agent's write permission. Stopping new damage comes before understanding the damage. A paused agent cannot extend a bad run while the record is read.
  2. Identify the change in the audit trail. List what the run actually did, in order, from the log — not from the plan it was supposed to follow.
  3. Sort each action by layer. Version restore, compensating action, or correction only. Anything in the third group gets its correction drafted now, while the facts are fresh.
  4. Roll back to the previous version where that layer applies. For a published app, restore to the checkpoint and republish; confirm which version users are actually seeing.
  5. Carry out the compensating actions in reverse order. Last action undone first, using the pairs written in advance, and tick each one off the audit list.
  6. Confirm recovery with health checks. Check the service, the data and one normal end-to-end task before declaring the incident closed.
  7. Write the incident record. Detection signal, time to stop, what was reversed, what was corrected, and what stays open.

What success looks like: write access is paused within the time the drill measured, every audited action is marked restored, compensated or corrected, health checks pass, and no action is left in an unknown state. An action nobody can classify is a failed rollback, even if the visible damage looks small.

The stop drill: time it, fix what slowed you

Rollback should be rehearsed in staging on a schedule, and the small-operator version of that rehearsal is a timed stop drill. Pick a harmless test run. Start it. Declare an abort without warning, and time three intervals: noticing the problem, pausing write access, and completing the manual fallback step.

The drill earns its time in one place: it exposes the slow step nobody suspected. A pause control buried in an admin screen, an audit log only one person can read, a compensating action that was never actually written — each surfaces in a drill at no cost, instead of during a real incident at full cost. Fix the slowest step, record the new times on the abort page, and drill again on the next cycle.

After the rollback: checks before the agent runs again

Do not restart on relief. Restart on evidence. The failure that caused the run goes into the agent's checks as a named case: the input that triggered it, the output that should have been caught, and the approval or stop rule that now sits in front of it. The compensating-action list gets any pair the incident proved was missing. The abort page gets the measured stop time from the real event, replacing the drill estimate.

One last distinction keeps the next incident smaller. Restoring the agent is separate from trusting it. The first runs after a rollback stay on the narrowest permission and the closest supervision the setup allows, and widen only after clean runs — the same staged trust the original setup should have used.
