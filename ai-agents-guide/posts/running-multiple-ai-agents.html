Running multiple AI agents without the pile-ups

One agent is a tool. Two agents are an organization — with an organization's failure modes: duplicated work, contradictory edits, and decisions nobody owns. The fix is not smarter agents. It is structure, written down in advance.

Published 2026-10-23 · Last updated 2026-10-23

First question: should there be a second agent at all?

Every multi-agent problem gets cheaper the earlier you ask whether it needs to exist. The clearest statement in the orchestration literature is also the least marketed: use the least complex option that meets the need. A direct model call handles single-step work; a single agent with tools handles varied requests in one domain and is often the right default; multi-agent orchestration earns its overhead only for cross-domain problems, work needing distinct security boundaries per agent, or genuine parallel specialization (s4). The reason is arithmetic, not conservatism: every added agent brings coordination overhead, latency, and cost of its own (s4). So the threshold test for a second agent is concrete. Name what the current agent cannot do reliably — a different specialty it performs badly, a permission boundary it should not cross, or a volume of parallel work it serializes too slowly. If the honest answer is "it could, with better instructions," improve the instructions. You are not collecting agents; you are staffing a workflow, and headcount is a cost centre.

The three ways agents collide

When multi-agent setups fail, they fail in three recognizable shapes. Duplicated work: two agents, both diligent, research the same question or draft the same reply because neither knew the other had it. Contradictory edits: two agents update the same record from different starting states, and the later save silently erases the earlier one. Contradictory decisions: agents acting on the same situation reach opposite conclusions — one approves, one flags — with no rule for whose call stands. Practitioner and platform guidance agrees on the root cause hiding under all three: conflict is largely what happens when agents run in parallel on the same data without structure. Sequence the work, partition the data, or govern the decisions — every working fix is one of those three (s1, s2).

Handoffs with contracts: the boring machinery that works

The proven shape is unglamorous. Define the sequence and the data flow explicitly: agent A runs, completes, and passes its output to agent B in a structured handoff — sequential by default, concurrent only where you deliberately designed it (s1). The hinge is the contract: exactly what structure each agent outputs and exactly what the next one expects as input. "A returns an array of objects with these fields; B consumes that structure and returns scored results in this one" — when contracts are written at that level, coordination becomes straightforward and the platform or schedule can enforce that B does not start until A is done (s1). Around the handoffs sits the coordination layer, in whatever size your setup affords: an orchestrator — a software layer or a designated agent — that decomposes the goal, assigns tasks to the right agent, resolves conflicts, aggregates output, and maintains the shared context so no stage starts from zero (s4, s5). At small scale that "layer" can be a schedule and a shared file; the functions, not the tooling, are what matter. One more mechanism, from practice: agents check a shared log before acting — the first agent logs its decision, the next reads the log, acts on what it finds, and logs in turn, so the whole chain is visible in one place (s3).

Decision authority: who wins, decided in advance

The authority row deserves the emphasis practitioners give it. In one documented order-processing setup, the inventory agent's word on stock availability overrides general business rules, while the payment agent holds a veto if payment fails — and the account stresses that all of it was configured upfront, not left to emerge (s3). Generalized coordination guidance says the same at the system level: pre-set rules resolve opposing results by trusting the designated agent for that question more, or escalating to a human where the case is unclear (s2). And the cost row is the one that surprises people: agents left running continuously made low-value decisions until budgets and event triggers replaced the always-on default (s3). Coordination, it turns out, is mostly a list of decisions you make once, in writing, while calm.

Add your second agent in six steps

  1. Pass the threshold test: write down what agent one cannot do reliably — specialty, permission boundary, or parallel volume. No named gap, no new agent (s4).
  2. Draw the boundary: list each agent's tasks and, just as explicitly, what it must never touch. One owner per workflow, one writer per record (s2).
  3. Write the handoff contract: the exact output structure of the first agent and the exact input the second expects, with a worked example (s1).
  4. Stand up the shared log: one place every agent reads before acting and writes after deciding, so state is shared rather than assumed (s3).
  5. Name the authorities: per topic, whose conclusion wins; which agent holds a veto; which cases escalate to you (s2, s3).
  6. Set budgets and triggers, then checkpoint: per-agent spend limits, event-based starts, and a stored decision at each stage so failures resume instead of repeat (s3).

What success looks like: a week of two-agent work with zero duplicated tasks, zero overwritten edits, every disagreement settled by a rule you wrote in advance, and a log a single daily review can audit — coordination as a quiet system, not a group chat you referee.

Questions people ask about running several agents

Do my agents need to "talk to each other"? They need shared state and defined handoffs, which is less romantic and more reliable than conversation: standard protocols exist for agent-to-agent messaging, but at small scale a shared log plus contracts delivers the same guarantees (s1, s2, s3).

What if both agents are right and still disagree? Then the disagreement is about values or priorities, not facts — exactly the case pre-set authority rules route to a human. Design the escalation; do not let the agents average their answers (s2).

How many agents is too many? The count where coordination work — contracts, logs, authority rules, reviews — grows faster than the work being coordinated. The ladder exists for a reason: add an agent only when the simpler shape demonstrably cannot carry the job (s4).
