Wi-Fi connected but no internet: find which link in the chain broke

Fixes · 8 min read

Why does the Wi-Fi icon look perfectly healthy while nothing loads? Because the icon reports on exactly one link: the hop between your device and the router. TP-Link's own troubleshooting guide puts it plainly — a device showing “connected” has reached the router, and the break sits somewhere further up the chain: the router's address handout, the router itself, the modem, or the provider. “Connected, no internet” is not one fault with ten possible fixes. It is four different faults sharing one symptom, and three quick tests tell them apart. Run the tests first. The fix for the link that actually broke is usually short.

The three tests that name the broken link

Test one: how many devices? Pick up a second device on the same network and try to load anything. TP-Link's guide draws the split the same way: if only one device has no internet, the problem is likely that device's settings; if every device is affected, the problem is likely the router, the modem, or the provider. This single observation halves the work — a whole-house fault is never fixed by resetting one laptop.

Test two: what address did the device get? On a Windows PC, open Command Prompt, type ipconfig, and read the IPv4 Address under the Wi-Fi adapter. If it starts with 169.254, the router never gave the device an address at all. Microsoft documents this fallback as Automatic Private IP Addressing (APIPA): the address range 169.254.0.0 to 169.254.255.255 is reserved for it, a Windows computer assigns itself an address from that range when no DHCP server answers, and such an address can only talk to other devices on the same local network — it cannot reach the internet, by design. A 169.254 address is not a vague error. It is the DHCP link, specifically, reporting itself broken.

Test three: can names be resolved? If the address looks normal (on most home networks it starts 192.168) and the router's admin page opens in a browser, but websites fail to load, suspect DNS — the system that translates a site's name into the address the device actually visits. TP-Link's guide notes that a misconfigured DNS can leave a device connected yet unable to load anything, even while the router and provider are working. That combination — local network fine, names failing — is the DNS link's fingerprint.

The procedure, in order

  1. Run the three tests above and write down the results. One device or all of them, the first four digits of the IPv4 address, and whether the admin page opened. Change nothing until the pattern is on paper — the pattern is what chooses the steps below.
  2. Restart the modem and router, in that order. Unplug both. Wait at least 30 seconds. Plug the modem back in first and let its lights settle, then plug in the router and give it a few minutes. A restart is the documented first step for the whole-house pattern: it clears the router's stalled address handouts and forces a fresh connection to the provider. Retest before going further.
  3. If one device fails, forget its network and rejoin. On Windows: Settings > Network & internet > Wi-Fi > Manage known networks, select your network, choose Forget, then reconnect and type the password again. On a phone: open the network's details in Wi-Fi settings and choose Forget, then rejoin. Apple notes that after router settings change, a device may need exactly this — forget and rejoin — so it picks up the new settings instead of replaying stale ones.
  4. If the address was 169.254, renew it. Open Command Prompt as administrator and run ipconfig /release, then ipconfig /renew. Run ipconfig again: a normal address means the router is handing out addresses again. If 169.254 comes back, the router's DHCP side is still not answering — restart the router once more (step 2) and check its admin page for a disabled DHCP server before touching the device again.
  5. If names were the failure, set DNS back to automatic. On Windows, following TP-Link's documented path: Settings > Network and Internet > Change adapter options, right-click the Wi-Fi connection, choose Properties, then Internet Protocol Version 4 (TCP/IPv4), then Properties again, and select “Obtain DNS server address automatically”. TP-Link's guide gives a public resolver, 8.8.8.8, as the alternative entry in the preferred DNS field. Test a site by name after the change.
  6. Still stuck on one Windows device? Run the documented command sequence. In an administrator Command Prompt, in this order: netsh winsock reset, netsh int ip reset, ipconfig /release, ipconfig /renew, ipconfig /flushdns — the sequence Microsoft Support publishes for this fault. Restart the PC and retest.
  7. Last resort on that device: Network reset. First write down anything custom — a VPN setup, a fixed IP address — because Network reset removes the network adapters and their settings, reinstalls them with defaults after the restart, and VPN software may need to be reinstalled. Microsoft's guidance is explicit that this should be the last step tried. On Windows 11 the path is Settings > Network & internet > Advanced network settings > Network reset > Reset now. Rejoin the Wi-Fi afterwards and retest.

What success looks like: the previously failing device shows a normal IPv4 address instead of a 169.254 one, loads three different websites by name in a row, and is still online after a restart of the device itself. Every other device in the house was untouched and stayed online throughout — that restraint is part of the success, because the fault was one link, not the whole chain.

When every device fails the wired test too: escalate with evidence

Plug a computer into the modem or router by Ethernet cable and test again. If wired browsing fails as well, and a proper restart changed nothing, the remaining links are the modem's line and the provider — home settings are finished. Call with the record from step 1 in hand: the fault affects every device, wired included; the modem and router were restarted in order at a stated time; the modem's internet light state; and how long the outage has run. That record moves the call past the scripted reboot suggestion, because the reboot in the script has already been done, in order, with the result measured. Keep the record if it recurs — a pattern of dated, wired failures is the evidence a provider cannot argue with.
