UDMA CRC Error Count: Is It the Cable or the Drive? A Baseline Test That Settles It

Drive health checks · Published 2026-11-02 · Last updated 2026-11-02

A high UDMA CRC Error Count does not mean the drive surface is failing. That is the myth to clear away first. Attribute 199 counts errors in data transfer via the interface cable, as determined by the Interface Cyclic Redundancy Check, usually shortened to ICRC. The suspect is the path between drive and computer: cable, connectors, port, or the drive interface itself. The platters and the flash memory are a different question, answered by different attributes.

That distinction changes the first move. Replacing a drive whose cable was loose wastes money and copies data for no reason. Ignoring a count that is still climbing misses a connection fault that will keep interrupting transfers. The count on its own settles neither case. Its movement, after one controlled change, settles both.

What attribute 199 counts, and what its neighbours count

In the Seagate SMART attribute specification, attribute 199 is listed as Ultra DMA CRC Error Count, with attribute ID 199 and hex code C7. SMART tools may label it UDMA CRC Error Count, UltraDMA CRC Error Count, or attribute C7. The labels differ. The counter is the same.

AttributeWhat it recordsFirst suspect
199 UDMA CRC Error CountErrors in data transfer via the interface cable, detected by ICRCCable, seating, port, or interface
197 Pending sectorsSectors the drive suspects and has not yet resolvedThe storage surface itself
198 Uncorrectable sectorsSectors that could not be read correctlyThe storage surface itself

Read 199 beside 197 and 198, never instead of them. A drive can carry a large CRC count from one bad cable years ago and have clean sector attributes today. A drive can also have a zero CRC count and growing pending sectors. Each attribute answers its own question, and mixing the answers produces the wrong repair.

Why the absolute number misleads

The CRC counter does not reset. A fixed cable leaves a permanent number behind, so the figure on screen today may be history rather than a live fault. Only a rising count shows an active problem. Forum reports from drive owners make the same point from the other side: UDMA CRC errors are communication errors between the drive and the host, they typically involve the drive, the SATA cable, or the motherboard, and the absolute count matters less than whether it keeps increasing.

So there is no safe number and no doomed number. A count of 3 that rose this week deserves action. A count of 800 that has not moved in a year is a record of a fault that may already be fixed. Anyone quoting a threshold without asking for two readings, taken on two dates, is guessing.

Short paragraph, plain rule: one reading is a photograph. Two readings are evidence.

The baseline and swap procedure

  1. Back up first if the data matters. Any drive under suspicion gets copied before it gets handled. The cable work below involves powering down and reseating connectors.
  2. Record the baseline. Open your SMART tool, note the raw value for attribute 199, and note attributes 197 and 198 beside it. Write the date next to the numbers. A screenshot saved with the date in the file name does the same job.
  3. Power down fully. Shut the computer down, switch off the power supply if it has a switch, and give the drive a moment to stop.
  4. Change exactly one thing. Reseat the data cable at both ends, drive end and motherboard or controller end, until each connector sits firmly. If a spare data cable is on hand, swapping the cable counts as the one change for this round. Do not also change the port in the same round.
  5. Use the machine normally for several days. Copy some large files if you want the interface worked harder than idle use works it. Note any disconnects or transfer errors with their dates.
  6. Read attribute 199 again and compare. Same tool, same drive, raw value against the dated baseline from step 2.

What success looks like: the raw value at the second reading matches the baseline exactly, attributes 197 and 198 have not risen, and no disconnects were logged during the test days. The fault was in the connection you reseated or replaced, and the old count is now just history.

Reading the result: the decision table

Second readingVerdictNext step
199 unchanged, 197 and 198 unchangedConnection fault, now fixedLog the new baseline and check monthly
199 still climbing after a reseatFault still in the pathNext round, change the cable if you have not, or move to a different port, one change only
199 climbing after cable and port changesDrive interface or controller now the likely suspectTest the drive on another computer if one is available, and plan replacement if it climbs there too
199 stable but 197 or 198 risingSeparate surface problemStop cable work, back up, and treat the drive itself as failing

The one variable rule is what makes this table usable. Change the cable, the port, and the drive bay in a single afternoon and a stopped count tells you a fix happened somewhere, without telling you where. That matters the day the fault returns and you need to know which part to touch first.

Where USB enclosures fit

An external drive adds parts to the path: a USB cable, an enclosure bridge, and often a separate power supply. The same logic applies, with one caution. Some enclosures and bridges do not pass full SMART data through at all, so a missing attribute 199 on an external drive may mean the bridge hides it, not that the count is zero. If the tool shows no SMART table for an external drive, the baseline test belongs on a direct internal connection, or it does not happen. A monitoring program running in the background helps here, because an SSD gives no audible warning as it ages, and a counter that only gets read during a crisis has no baseline to compare against.

The decision, stated plainly

Treat attribute 199 as a witness for the connection, not a verdict on the drive. Record it, change one part of the path, read it again. Still and stable means the repair worked and the number can be ignored as history. Still climbing after cable and port rounds means the suspicion moves, with evidence, to the drive interface or the controller. And if the sector attributes start moving at any point, the question has changed entirely: copy the data off and replace the drive, whatever the cable was doing.
